1. Introduction

This is a simple specification aimed at assisting developers building algorithmic-based MCP / CLI agentic tooling which have high Developer and Agent Experience (DX/AX). The majority of MCPs and CLIs relate to accessing data, however there is a growing demand for agentic tooling which surface algorithms such as predictive model inference, business logic and optimisation. The vast design and execution space for these tools, caused by their flexible nature, often results in poor AX and inconsistent implementation / documentation. Much of this information ends up buried in tool descriptions as free text — algoto provides a structured, machine-readable format for it instead.

This spec attempts to close this gap, covering foundational elements of the design space for algorithms. A development team which builds many sets of agentic tools, surfacing a wide range of algorithms, will benefit from having a common specification for their tools to adhere to. This specification extends and builds on top of MCPs annotations (agent hints), setting out guidelines specific for this class of tooling. It isn't intended as an industry standard, just a practical format for keeping this kind of tooling consistent. Success would be finding a way to fold some of these ideas into the protocol layer itself, rather than asking people to converge on this.

Much of what an algoto document expresses could, in principle, live in your source code — but MCP has no way yet to annotate most of it, so it never reaches the agent. Function signatures, type hints, default values, docstrings and validation rules already surface through the tool definition. algoto adds a structured place for the things that are only expressed via the source code itself: what class of algorithm is running, whether it's deterministic, how each input shifts the output, what the numbers in the response actually mean, and what to do when something fails.

Your source code already definesalgoto adds
Function name, docstring, parameter namesAlgorithm family (prediction, simulation, etc.), method summary, internal steps
Type hints, default values, validation boundsWhether the algorithm is deterministic, approximate, or seeded
Input parameter types and validationEach input's role (data vs tuning parameter), its effect on the output, its units, and what happens when it is omitted
Return type and response shapeWhat each output field means, its units, and how uncertainty is expressed

Exception types and error responsesWhen each error fires and what the caller should try next

2. For Agent Developers

An algoto document surfaces things the tool's signature has no structured way to annotate yet. Here is how to act on each section.

2.1 Caching

When deterministic is true, identical inputs will always produce identical outputs. Your agent can cache and reuse results for repeated calls without re-invoking the tool.

2.2 Parallelism

When parallelisable is true, multiple calls can run concurrently with no shared state. Your agent can fan out batch work safely. When absent or false, calls should be sequential.

2.3 Input planning

Use role to understand what each input does. data inputs are what the tool operates on — the agent should source these from upstream tools or the user. parameter inputs tune behaviour — the agent can adjust these to control the output. Read the effect field before choosing a value: it describes the trade-off in plain language. When omission is present, it tells you what the tool does when the input is left out — use it to decide whether the default behaviour suits the task or whether you need to override it.

2.4 Interpreting outputs

Check interpretation before presenting results to the user. It explains what the numbers mean and how to act on them. If uncertainty is present, surface the confidence information alongside the point estimate — don't discard it.

2.5 Guardrails

Read constraints before constructing a call. They describe cross-input rules the tool will enforce. Violating a reject constraint wastes a round trip; the agent should check the rule client-side first. The description field suggests what to do instead.

2.6 Latency and async

Use latency to set user expectations. If the value is minutes or long, inform the user before calling. For async tools with a poll_tool, use the declared poll_interval rather than polling aggressively.

2.7 Error recovery

The errors array lists known failure modes. When a call fails, match the error against the when conditions and follow the hint — it tells the agent what to try next, avoiding blind retries.

3. Example

A forecasting tool written the usual way:

@mcp.tool()
def forecast_demand(
    history: list[Observation],
    horizon_days: int = 14,
    interval_level: float = 0.9,
) -> Forecast: ...

The algoto document beside it:

{
  "algoto": "1.1",
  "name": "forecast_demand",
  "algorithm": {
    "type": "prediction",
    "description": "Seasonal exponential smoothing with a weekly cycle, fit per call on the supplied history.",
    "steps": [
      "Validate and gap-fill the sales history",
      "Fit trend and weekly seasonality components",
      "Project forward over the requested horizon",
      "Derive prediction intervals from in-sample residuals"
    ],
    "deterministic": true,
    "version": "2.1.0"
  },
  "inputs": {
    "history": { "role": "data", "units": "units/day" },
    "horizon_days": {
      "role": "parameter",
      "units": "days",
      "effect": "Longer horizons widen the prediction intervals.",
      "omission": "A 14-day horizon is used, suited to short-term operational planning."
    },
    "interval_level": {
      "role": "parameter",
      "units": "probability 0–1",
      "effect": "Higher coverage widens the bounds; the point estimate is unaffected.",
      "omission": "A 90% prediction interval is returned."
    }
  },
  "outputs": {
    "forecast": {
      "units": "units/day",
      "uncertainty": "lower/upper bounds at the requested interval_level accompany each point estimate",
      "interpretation": "The point estimate is the median outcome; plan capacity against the upper bound."
    }
  },
  "guardrails": {
    "constraints": [
      {
        "rule": "horizon_days <= length(history) / 2",
        "on_violation": "reject",
        "description": "Supply more history or shorten the horizon."
      }
    ]
  },
  "execution": { "mode": "sync", "latency": "instant" },
  "errors": [
    {
      "when": "history contains fewer than 28 days after gap-filling",
      "hint": "Fetch a longer sales history and retry."
    }
  ]
}

You could put all of this in a tool's description string, but algoto gives a formalised, machine-readable structure for expressing it — consistent across tools and teams.

4. Attachment to Agent

The document itself is the same everywhere; there are a number of different mechanisms for delivering it to an agent, depending on the protocol the tool is exposed through.

4.1 Tool name

name must exactly match the tool it annotates — the MCP tool name or CLI subcommand. This is the join key that links the document to the tool.

MCP servers must attach the document under the _meta key alsgregory.github.io/algoto. A single, fixed key is what makes documents discoverable — an agent or linter can look for exactly that string across every server.

4.2 MCP servers

Use the MCP protocol's _meta field on the tool definition to attach the document. This keeps the annotation structured and exposes the document to the client.

import json
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("forecasting")

ALGOTO_DOC = {
    "algoto": "1.1",
    "name": "forecast_demand",
    "algorithm": {
        "type": "prediction",
        "description": "Seasonal exponential smoothing with a weekly cycle.",
        "deterministic": True,
        "version": "2.1.0",
    },
    "inputs": {
        "horizon_days": {
            "effect": "Longer horizons widen the prediction intervals."
        }
    },
    "outputs": {
        "forecast": {
            "units": "units/day",
            "interpretation": "The point estimate is the median outcome."
        }
    },
}

@mcp.tool(meta={"alsgregory.github.io/algoto": ALGOTO_DOC})
def forecast_demand(
    history: list[dict],
    horizon_days: int = 14,
    interval_level: float = 0.9,
) -> dict:
    """Forecast demand from historical observations."""
    ...

4.3 CLI

Ship a sidecar <tool_name>.algoto.json and support --algoto on each subcommand to print it.

4.4 Validation

Any JSON Schema 2020-12 validator can check a document:

check-jsonschema --schemafile algoto.schema.json forecast_demand.algoto.json

On the repository's README there are more examples of how to add validation into your workflow.

6. Algorithm

Describes what the tool does under the hood.

PropertyTypeDescription
typeenumprediction, classification, optimisation, simulation, estimation, transformation, other.
descriptionstringOne plain-language line describing the method.
stepsarray of stringShort list of internal steps, in order.
deterministicbooleanTrue when identical inputs always produce identical outputs. Agents can use this to cache results for repeated calls.
parallelisablebooleanTrue if multiple calls can safely run concurrently with no shared state or ordering dependency.
seed_inputstringName of the parameter that pins randomness.
approximatebooleanTrue if the output is an approximation (heuristic, time-bounded, sampling-based).
versionstringAlgorithm version. Bump when outputs change for identical inputs.
"algorithm": {
  "type": "prediction",
  "description": "Seasonal exponential smoothing with a weekly cycle, fit per call on the supplied history.",
  "steps": [
    "Validate and gap-fill the sales history",
    "Fit trend and weekly seasonality components",
    "Project forward over the requested horizon",
    "Derive prediction intervals from in-sample residuals"
  ],
  "deterministic": true,
  "version": "2.1.0"
}

7. Inputs

Per-parameter annotations, keyed by the exact parameter name. Each annotation must contain at least one property.

PropertyTypeDefaultDescription
roleenumparameterdata is what the tool runs on, parameter tunes it, seed pins randomness.
effectstringHow changing this input moves the output.
unitsstringUnits or scale.
omissionstringWhat the tool does when this input is absent — the behaviour that takes effect, not the raw default value.
"inputs": {
  "history": { "role": "data", "units": "units/day" },
  "horizon_days": {
    "role": "parameter",
    "units": "days",
    "effect": "Longer horizons widen the prediction intervals.",
    "omission": "A 14-day horizon is used, suited to short-term operational planning."
  }
}

Types, default values, descriptions, required flags and enum values belong in the tool's input schema, not here. omission complements (not replaces) a default value: it describes the consequence of leaving an input out, which a raw value like 14 cannot convey.

8. Outputs

Per-field annotations, keyed by field name. Each annotation must contain at least one property.

PropertyTypeDescription
unitsstringUnits or scale of the field.
uncertaintystringHow uncertainty is expressed for this field.
interpretationstringHow to read the value.
"outputs": {
  "forecast": {
    "units": "units/day",
    "uncertainty": "lower/upper bounds at the requested interval_level accompany each point estimate",
    "interpretation": "The point estimate is the median outcome; plan capacity against the upper bound."
  }
}

9. Guardrails

Cross-input constraints and rate limits, stated so agents do not discover them by trial and error.

PropertyTypeDescription
constraintsarrayRules across parameters. Each has a rule, optional on_violation, and optional description.
rate_limitstringCall budget in plain words.

9.1 Constraint fields

PropertyTypeDefaultDescription
rulestringReadable constraint over parameter names. Not machine-evaluated.
on_violationenumrejectreject or warn.
descriptionstringWhat the agent should do instead.
"guardrails": {
  "constraints": [
    {
      "rule": "horizon_days <= length(history) / 2",
      "on_violation": "reject",
      "description": "Supply more history or shorten the horizon."
    }
  ]
}

10. Execution

PropertyTypeDefaultDescription
modeenumsyncsync or async.
latencyenumundeclaredinstant (<1s), seconds (<30s), minutes (<10min), long.
asyncobjectPolling hints when using a paired-tool async pattern.

10.1 Async

The async block is only relevant when protocol-level async (such as MCP Tasks) isn't supported. Where it is, the protocol owns the polling mechanism and no async block is needed. Declare poll_tool only when the server falls back to a paired-tool pattern — a start tool plus a separate result-retrieval tool.

PropertyTypeDescription
poll_toolstringCompanion tool to poll for results.
poll_intervalnumberPolling interval in seconds.
"execution": {
  "mode": "async",
  "latency": "minutes",
  "async": {
    "poll_tool": "get_schedule_result",
    "poll_interval": 10
  }
}

11. Errors

Known failure modes with recovery hints. Error codes and response shapes stay in the tool definition.

PropertyTypeRequiredDescription
whenstringyesCondition that triggers the error.
hintstringnoWhat the agent should do next.
"errors": [
  {
    "when": "history contains fewer than 28 days after gap-filling",
    "hint": "Fetch a longer sales history and retry."
  }
]

12. Trust

An algoto document is metadata. Trust it exactly as much as you trust the tool's author.
